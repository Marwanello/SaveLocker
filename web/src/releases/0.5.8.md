# v0.5.8

_Released 16 August 2026_

**A Steam Deck with an update waiting can now install it without a terminal.** Until this release the
Game Mode screen told you an update was ready and gave you nothing to press — and the sentence it used
to explain itself was, on inspection, not something anyone could act on.

No database changes. No save data is touched by upgrading.

## "Nothing to do" was a dead end

A Deck with an update waiting showed exactly this, and nothing else:

> SaveLocker 0.5.7 is ready and will be installed the next time this device starts SaveLocker.
> Nothing to do.

Every word is true. It is still the wrong answer for someone who wants the update now:

- **"the next time this device starts SaveLocker" does not mean a reboot** — it means SaveLocker's
  background service starting. Nothing on the screen said so, so the only way to know was to guess.
- **"Nothing to do" reads as "you cannot do anything."** In Game Mode that was accurate, and it should
  not have been.
- The routes that did work — `savelocker update`, or restarting the service by hand — both need
  Desktop mode and a terminal, which is not where anyone is reading that notice.

That screen now tells you what actually applies the update, **and it checks your device before saying
it**. See below for why that check matters.

## What does and does not install a waiting update

This table is now in the help article too, because the wrong guess is a very natural one:

| Action | Installs a waiting update? |
|---|---|
| Restarting your Deck | **Yes**, always |
| Switching to Desktop mode and back | Usually yes — but **not** if you have enabled *lingering* |
| `savelocker update` | Yes |
| **Restart Steam** (in the power menu) | **No** |
| Sleep and wake | No |
| Closing a game | No |

**Restart Steam is the one to know about.** It is the control actually on the screen, it is the first
thing anyone reaches for, and it does nothing here — SaveLocker is not one of Steam's processes.

**The lingering row is why the Game Mode screen checks your device rather than telling everyone the
same thing.** Switching to Desktop mode and back works because it logs you out and back in, which
restarts your background services with it. If you have run `loginctl enable-linger` — which this
console's help recommends in three places, as the fix for the agent stopping when you log out — those
services keep running, and the mode switch changes nothing. Your Deck now reads its own setting and
tells you only what is true for it.

## The Decky plugin can do it for you

If you use the optional [Decky Loader](https://decky.xyz) plugin, **SaveLocker-Decky v0.2.1** adds an
**Install update now** button to its panel. It restarts the agent for you, waits for it to come back,
and tells you which version you ended up on — without leaving Game Mode.

The button appears **only when the update is already downloaded and verified**, never for one that has
merely been announced. Those are genuinely different situations: the first is a file copy that works
with no network at all, the second needs a download that can fail or sit there.

**If a game is running, the button is replaced by a note naming it.** SaveLocker deliberately waits
for a game to close before replacing its own files, so restarting mid-game succeeds and installs
nothing — which is the most confusing thing a button can do.

Update the plugin the way you normally do; if you have uploaded a plugin package in **Configuration →
Agent updates → Decky plugin**, your agent will fetch it by itself.

## The console and `doctor` stopped saying something untrue

Two places still told Deck owners to update by hand — the agent's own **Settings → Updates** panel and
`savelocker doctor` both said to download a tarball and re-run `install.sh`. That has not been
necessary since v0.5.5. Both now distinguish an update that is *available* from one that is
*downloaded and ready*, and say what will happen next.

`savelocker doctor` also reports a waiting update even on a machine whose enrollment has been lost —
which is exactly when someone runs it.

## What has and has not been tested

The agent half is covered by the automated Linux suite, which grew eight checks for this and was run
against deliberately broken builds to confirm those checks can actually fail.

**The Decky button has not been used on hardware.** The uncertain part is whether Decky's plugin
backend can restart a user service at all; if it cannot, the panel shows the exact reason rather than a
generic failure, and restarting the Deck always works. Nothing about this can leave an agent in a bad
state: the update it installs is the same one that would have gone in at the next start.

## Before you upgrade

- **Update the agents.** The whole of this release is agent-side; the console half is the help article
  and the notes you are reading.
- **Decks running v0.5.5 or later update themselves** once the Linux tarball is uploaded in
  **Configuration → Agent updates**. Older Decks need one hand-run of `install.sh`.
- Windows agents update themselves once the installer is uploaded in the same place. Nothing is
  offered to either fleet until those rows are filled.
- **No database changes.** Downgrading the container is a clean rollback.
