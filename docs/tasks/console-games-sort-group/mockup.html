Games tab — sorting & grouping, three ways

Today the Games tab shows one flat list (or wall) in upload order, and the only preference is List / Grid. This mockup adds grouping — Device, Platform (with emulator sub-groups), Source, Date added, Date synced, Status — and sorting — Name, Recently synced, Recently added, Size — in three different interaction designs. All three frames are live: click the controls, collapse groups, switch layouts, pick games. Same sample fleet in every frame.

v1 note (2026-10-12): Option A shipped without Date added — the database has no created column yet (plan.md carries the follow-up); its frame below still shows it as designed. Everything else here is live in the console.

What each option needs
Option A

Toolbar — the controls live where the list lives

Two compact dropdowns, Group and Sort, sit in the sidebar header (list layout) or the page head (grid layout). Always visible, one click to any arrangement; groups render as sticky section headers with counts.

Try it in the frame

  • Open Group — None, Device, Platform, Source, Date added, Date synced, Status
  • Open Sort, pick Size, then flip the arrow
  • Collapse a group · switch List/Grid · click a game
Option A — Toolbaropens in Grid; switch to List for the sidebar controls

Where it wins

  • Nothing is hidden: the arrangement is always on screen and one click away.
  • Reuses the layout switch's own place and pattern — no new concept in the sidebar.
  • Group headers stay sticky and scannable in both list and wall.

What it costs

  • Two more controls in a 250 px sidebar; on a 5-game library that is noise.
  • Seven group choices behind a small button, with no room to say what any of them mean.
  • Turns the sidebar header into the busiest strip on the page.
Option B

Organize — one button, one panel, everything explained

A single Organize button opens the whole arrangement: group choices and sort choices, each with a line saying what it does, plus direction and reset. The active arrangement is stated under the button and on the page, and group headers carry the facts — count, size, last update.

Try it in the frame

  • The panel is open — pick Platform, then Date synced, then Status
  • Flip the direction row, try Reset, close with Done
  • Collapse a rich group header · switch List/Grid
Option B — Organizeopens in List with the panel showing; rich group headers

Where it wins

  • Room for every choice and a sentence about each — the only option that can explain itself.
  • Quiet toolbar; one button does not crowd the sidebar or the page head.
  • Easiest to grow later: filters, saved arrangements, per-group actions all have a home.

What it costs

  • The arrangement is invisible until the button is opened — needs the state line to compensate.
  • Changing groups costs a click more than Option A.
  • One more popover pattern to keep dismissible and keyboard-usable.
Option C

Shelves — grouping becomes the view

Group-by chips run across the top; each group is a full-width shelf of covers with a heading and its facts, and the shelf sits beside List and Grid as a third layout. Built for browsing a wall of covers by platform or device; the same grouping also drives the list and wall layouts.

Try it in the frame

  • The chip row is the group control — try Device, Source, Date added
  • Sort at the right, then flip direction
  • Collapse a shelf · switch List/Grid/Shelves
Option C — Shelvesopens in the Shelves layout, grouped by Platform

Where it wins

  • Grouping is visible at a glance — no menu to open, no state to remember.
  • Platforms and devices read as collections; the best option for a big library on a big screen.
  • Emulator sub-groups (GameCube → Dolphin / PrimeHack) get a natural home.

What it costs

  • The most new layout code of the three; a third layout to maintain and test.
  • Horizontal scrolling inside a page that already scrolls vertically.
  • Seven chips plus sort compete for one row; the list layout still needs its grouped form.

Shared semantics, and what the build will need

All three options use the same grouping and sorting rules — only where the controls live and how the groups are drawn differ. These are the rules the frames actually implement; the questions under them are the calls to make before this is built.

Grouping rules in the frames

  • Device — one group per machine; a game on two machines appears under both, so group counts sum above the library size. The alternative is one group per game, keyed to the machine that last synced — simpler counts, but "what is on my Deck" needs a filter instead.
  • Platform — PC first, then each console; when a console's games come through two or more emulators (GameCube here: Dolphin and PrimeHack), the group splits into emulator sub-headers.
  • Source — Steam, Heroic, Playnite, Emulator, Save-folder scan, Added by hand. When machines disagree about one game, the row shows the first plus "N sources", like the existing chip on the game page.
  • Date added / Date synced — Today, Yesterday, Earlier this week, This month, Earlier; a game with no saves yet lands in "Never synced" last.
  • Status — Conflict, Needs attention, Synced, No saves yet, Disabled, using the same standing rule as the dot in the list today.

Sorting rules

  • Sorting applies within each group; flipping direction reverses every group at once.
  • Natural defaults: Name A–Z, Recently synced and Recently added newest first, Size largest first. A game with no saves sorts last under date and size, whichever direction is chosen.
  • The chosen grouping, sort and direction persist per browser, next to the existing sl_games_layout preference. Default is no grouping — today's screen.
  • Grouping changes nothing but the view: Sync all, commands, conflicts and counts are untouched.

Data the build needs (server, all additive)

  • Ready today: name, size (total and head), last synced, conflict/problems status, emulators and the release console of emulator games.
  • Date added: Game has no created column. Add Game.CreatedAt (+ migration); backfill existing rows from each game's first version where one exists.
  • Device groups: the overview carries no per-game machines. Add one batched field from MachineSavePaths (machines actually syncing it), optionally unioned with MachineGameSources for games found but not set up.
  • Source groups: likewise — one batched read of MachineGameSources for the whole overview (not one request per game).
  • Everything else is computed client-side from the existing 15 s overview poll.

Calls to make

  • Device model: overlap (game under each machine) or one group per game by last-synced machine?
  • Should the date buckets be calendar-based (Today / Yesterday / This week) or rolling windows?
  • Do collapsed groups stay collapsed across reloads, or reset each visit?
  • Does grouping belong in the sidebar list at all, or only in the wall and shelves?
  • Which option — or a mix (e.g. B's panel with C's shelves)?
