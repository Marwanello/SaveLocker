# Notifications: buttons that act, and a check on real installs (left by Group 7)

Not started. Moved out of `Backlog.md` on 2026-10-01; the notes below are as they stood there.

Source: `tasks/checkpoint-ui/implementation-grouping.md` → Group 7. (c), a popup on a real Linux desktop, was confirmed live on a Deck 2026-09-27.

- (a) *"Retry now" / "Install now" on a Windows toast* — a link cannot reach into the tray, and a custom URL scheme is refused by the toast host (measured, `Gotchas` → Windows notifications). The supported route is a COM activator: a Start shortcut carrying `ToastActivatorCLSID` (Inno has the parameter) plus `INotificationActivationCallback` in the tray — real work, and only testable with a shortcut the rig does not have yet.
- (b) *Run the installer once* and look at a real toast: the shortcut's `AppUserModelID` compiles under ISCC and the mechanism was proven with a scratch shortcut, but the installed agent's header has never been seen.
- (f) *A real installed `savelocker.service` never gets the desktop session's environment.* `default.target` is reached before SteamOS imports the session's variables into the `systemd --user` manager. This was confirmed on a real Deck, not just the test rig: the installed daemon still had Game Mode's values while in Desktop Mode. The click works around it by borrowing the session's values each time (`DesktopNotifier.Open`, Gotchas.md → Linux agent). Anything else the daemon launches into the desktop would need the same. Reordering the unit would need its own reasoning about Game Mode's session timing.
- (d) *The exe grew ~8 MB* for the WinRT projection (`Microsoft.Windows.SDK.NET.dll` + an unused `Microsoft.Windows.UI.Xaml.dll`); `CsWinRTIncludes` limited to `Windows.UI.Notifications`/`Windows.Data.Xml.Dom` would shrink it.
- (e) *`testenv.ps1 clean` printed "removed" and left the Windows state (an old API key) in place once*, giving a 401 on the next seed; deleting it by hand worked; cause not found. **Seen again 2026-09-28, with a clue:** the state had been created by a test tray started from an *elevated* shell (stopped just before). `clean` only prints "removed" when `Remove-Item` did not throw, yet every file was still there afterwards with its original timestamps; the same `Remove-Item` from the same unelevated shell a few minutes later, rig stopped, removed it. Suspect: elevated WebView2 helpers still holding the folder, invisible to `Stop-Windows` (it matches them by a command line an unelevated shell cannot read). Checking `Test-Path` after the removal would at least turn it into an error.
