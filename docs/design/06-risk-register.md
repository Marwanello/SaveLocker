# Risk register

Read the preceding documents first. Each risk below is scoped to what this design actually
introduces or touches — pre-existing risks unrelated to conflict resolution are not repeated here.

| Risk | Likelihood | Impact | Mitigation |
|---|---|---|---|
| **Steam UI update breaks the game-page route patch** (`routerHook.addPatch` on `/library/app/:appId`) | Moderate-to-high over time — Valve does not version this surface, and this codebase's own history already documents a related Steam-internals break (`SteamClient.*` "undocumented Valve internals... breaks on Steam client updates," accepted cost in `logs/2026-08-15_decky-plugin.md`) | Medium — the chip stops appearing on the game page, but nothing about sync safety depends on it | The QAM panel (`03-platform-ux-flows.md`) is not built on the route patch at all and is the guaranteed fallback; `doctor`/agent-ui conflicts page are further-still fallbacks. A broken patch degrades reachability, never correctness — no conflict is ever silently auto-resolved because a UI element vanished. |
| **Daemon is down when a frontend tries to show or resolve a conflict** | Low-moderate (daemon crashes, machine rebooting, agent not yet installed) | Low-medium — user sees a clear "agent not running" state rather than a wrong one | Already the existing pattern for the Decky launch-options card ("The SaveLocker agent is not running") and extended verbatim to the chip (`03-platform-ux-flows.md` → Backend communication). Nothing destructive can happen with the daemon down, because nothing can happen at all — no local writes occur outside a running `SyncEngine`. |
| **Clock skew between a Deck and a PC** | Certain — two independent devices, no NTP guarantee assumed | Would be severe if timestamps drove resolution | Not a risk in this design: detection is causal (parent-pointer vs. server head, `01-conflict-model-spec.md` §0), never clock-based. Timestamps shown in the chooser are informational only, sourced from `SaveVersion.CreatedAt` (server-assigned at upload, not agent-assigned), so even a badly-skewed agent clock cannot corrupt the *decision*, only the *display* — and even the display uses the server's clock, not the agent's. |
| **Partial writes during a snapshot or a resolution's pull** | Low — the underlying mechanisms (`ArchiveStore` staging, `SaveArchive.RestoreArchive`'s staging-dir-then-swap) are pre-existing and already interruption-safe | High if it ever happened — a half-written save directory | No new write path is introduced by this design; every commit-before-choose push and every resolution-triggered pull goes through the existing atomic archive/restore machinery unchanged. The one genuinely new write is `PrepareLaunchAsync`'s pre-launch push attempt, which is not a new *mechanism* — it's an existing, already-safe `PushAsync` call made from a new call site. |
| **Two devices resolve the same conflict simultaneously** | Low but real — the whole scenario this feature exists for (a Deck and a PC both able to act) | Low — the loser gets a clear, non-destructive answer | `02-resolution-api.md` §Layer 1: the second `ResolveConflictAsync` call loses the database's own atomic `Status != Open` check and returns `409`, surfaced to every frontend as "already resolved" rather than a generic error or (worse) a silent double-apply. Nothing about this needed new locking — the existing single-row update this method already performs is already atomic per request. |
| **Save paths that move between when a conflict opens and when it's resolved** (a relocated install, a remapped `MachineSavePath`) | Low-moderate, and pre-existing in the codebase (Wine/Proton prefix relocation is a documented, previously-fixed bug class — `Decisions.md`, Borderlands 2 case) | Medium — a resolution's queued pull could target a path that no longer holds the game | Not new to this design: `SyncEngine.PullAsync` already re-validates the save path immediately before restoring (`RefuseUnsafePath`, called twice — once at entry, once right before the write, per `Decisions.md`'s "validated at five entry points, re-checked again right before use" pattern), so a moved/invalidated path is caught at the same choke point a resolution-triggered pull already goes through, with no special-casing needed for "this pull came from a conflict resolution" vs. any other pull. |
| **Cloud-provider / server rate limits** (SteamGridDB, GitHub release-fetch — the only external rate-limited dependencies in this codebase today) | N/A to this design | N/A | This design adds no new calls to either — conflict resolution is entirely between agents and the self-hosted server. Included here only to state explicitly that it was considered and found not applicable, rather than left unaddressed. |
| **A Playnite plugin crash inside `OnGameStarting`** | Moderate — third-party plugin execution inside a host process not fully under this project's control | Medium — a thrown exception in a Playnite event handler could, depending on Playnite's own error handling, either be swallowed (silently skipping the gate) or surface as a Playnite-level error | Mitigate by wrapping every call from the plugin into the agent's local API in try/catch that defaults to **not blocking launch** on any unexpected failure — a plugin bug must degrade to "no pre-launch gate, same as today's baseline behavior," never to "the user can't launch anything." This mirrors `ProtonRun.ExecuteAsync`'s own existing rule ("a failure here must never stop it starting: a save-sync tool that prevents you playing is worse than one that misses a sync"). |
| **`OnGameStopped` not firing for a Playnite game wrapped by an emulator/second launcher** (confirmed real, documented Playnite limitation — `03-platform-ux-flows.md`) | Moderate, for the subset of Playnite users who wrap emulators through it | Low — this design already keeps `Watchers.cs`/`ProcessWatcher` as the exit-push fallback, unchanged | No new mitigation needed beyond not removing the existing fallback — flagged here so it's not later "fixed" by deleting `ProcessWatcher` in favor of the Playnite hook, which would reintroduce exactly the gap this row describes. |
| **A new D-Bus dependency (`org.freedesktop.Notifications` client) for desktop notifications** | Certain if built — this is genuinely new surface, not an extension of anything existing | Low-medium — mostly a build/maintenance risk (an added NuGet dependency, a new native/runtime interop path on Linux), not a safety risk, since it's purely an additional notification rung above a system (rungs 1-2 and 5-7) that already works without it | Scope as optional/deferred (phased plan) — no invariant in this design depends on rung 3 existing; rungs 1, 2, 4, 5, and 7 alone already satisfy every "no UI is load-bearing" / "fail closed" requirement without it. |
| **A losing conflict side is never protected on an auto-resolving policy** (`NewestWins`/`PreferMachine`), unlike a manual `keepBoth` resolve | Moderate — this is an *existing* behavior this design does not change, but the new pre-launch commit-before-choose path (model spec §2) makes an auto-loss happen more often (every pre-launch check under an auto-policy, not just explicit pushes) | Medium — under retention pruning, an auto-resolved loser is not specially protected and could eventually be pruned like any ordinary non-head version | Flagged explicitly in `07-open-questions.md` rather than silently decided — this design does not change today's retention behavior for auto-resolved conflicts, but increasing how often auto-resolution fires (by adding the pre-launch path) increases how often this pre-existing behavior is exercised, which is worth the maintainer's own call before shipping. |
| **A resolution attempted while offline is silently lost** | Low, by construction | Would be high if it happened — the exact "guess" the invariants forbid | Explicitly designed against in `02-resolution-api.md` §4: a resolve attempted with no connectivity returns `503` and changes nothing, rather than being queued and replayed blind later. The risk is therefore "a confused user who doesn't understand why," not data loss — mitigated by the fail-closed message being explicit about why and what to do next. |
